# Implementation

## Coverage

- Shared proposal and inventory schemas define `tuckmark.agent-import.v1`, scope-only template applicability metadata, independently editable label print quantities, non-blocking attention, and one Markdown device-detail string.
- DEVD owns shared template and inventory data, 30-minute authenticated sessions, template-input events, stale-response rejection, expiry cleanup, serial inventory commits, and recoverable all-or-nothing writes. Agent Import accepts template choices from the DEVD catalog only; browser-local templates can enter the shared directory solely through an explicit archive import.
- `DevdDataService` is the shared deep module for RuntimeStore, inventory, Agent Import, archive, revision persistence, transaction recovery, atomic JSON replacement, and SSE invalidation. It records durable directory ownership and holds a PID-scoped live lock before serving mutations, recovering only locks left by dead processes. Web `server-http` adapters for DEVD-owned records never fall back to browser storage; their resource commands are serialized locally so a completed revision always becomes the next expected revision. Concurrent read consumers share one in-flight runtime snapshot, preventing duplicate startup reads from surfacing an already superseded response. An SSE invalidation detaches that request, forces the next consumer to refetch, and prevents the late response from being accepted.
- The data HTTP contract exposes status, runtime snapshots and commands, inventory queries and commands, archive inspection/import/export, backup creation, and revision SSE. Only loopback transport peers may use DEVD routes. Archive merge is pure-new and conflict-atomic; replace writes a protection snapshot in the same transaction after duplicate and cross-record reference validation. Browser-static and server-http write the same `tuckmark.runtime-export-archive.v1` directory-tree ZIP and verify its required settings entry and manifest counts before import; `tuckmark.data-archive.v1` single-snapshot ZIP files remain readable. DEVD manual and protection snapshots retain every durable runtime and inventory record, while locks, transaction journals, and session credentials stay outside backups. Server-owned template history preserves the existing 20 saved-version, 10 autosave, five-minute autosave, and 20 protection-snapshot retention contracts.
- `tuckmark agent-import` provides catalog, inventory, create, open, wait, and fulfill commands over named IPC instances. Credentials persist the instance name, never a DEVD URL. Confirmation links use an independently configurable `--web-url` / `TUCKMARK_WEB_URL` and do not determine the native transport. The Canvas workspace edits one literal suggested-use string as template metadata in a compact multiline field, while the Templates workspace batch-entry table remains dedicated to variable data. Old persisted suggestion arrays are normalized while reading and all new writes use the singular field. DEVD, browser stores, and the CLI distinguish an omitted suggestion from a present empty string so unchanged data preserves metadata and an explicit clear removes it. No score, badge taxonomy, or recommendation weight is introduced.
- Named IPC is implemented by `@tuckmark/ipc`; it validates a required instance name, derives a per-user Unix socket or Windows Named Pipe, reuses HTTP route/schema/status contracts, rejects occupied endpoints, and recovers stale Unix socket paths. The server can expose HTTP and IPC listeners for the same DEVD app, while the Web remains HTTP-only.
- User template metadata patching updates `name`, `description`, and `recommendedUse` without creating a saved version and synchronizes the current working copy. Complete package saves continue to create saved versions. System templates are not represented as mutable DEVD records, and revision conflicts are returned without automatic replay.
- The `/agent-import/:sessionId` confirmation route presents two row-oriented editable tables: primary new-material and restock intake cells display plain values until clicked, then edit that single cell. `Enter` and blur return to display mode; `Escape` restores the value held when editing began. Supplementary fields, the label preview, and template fields expand in a detail row. `description` is edited as the concise overview, while `deviceDetails` remains a single Markdown source string with a safe rendered view; raw HTML is skipped and remote images become inert alternative text rather than network requests. The string is retained on the confirmed material. System previews use built-in definitions; user-template previews compile the authoritative DEVD working copy, falling back to its saved version. The preview work area is non-white so the white rendered label retains a visible physical boundary. Loading and unavailable states are explicit and never imitate a rendered label with concatenated text. The import-selection column uses a compact checkbox without redundant state text, and the compact action column keeps its controls within the desktop table width. It supports DEVD catalog template choices, template wait states, stale-poll rejection, and a Storybook state gallery. Existing-material fields are displayed read-only because a restock persists only an inbound adjustment; service updates likewise retain their original target, timestamp, and material identity. After DEVD returns a completed confirmation, the page replaces the session route with the active Web base path's `/inventory` route so the newly written records are immediately visible. The mock-only desktop result is recorded in `SPEC.md`.
- Recent-template and recent-print panels retain their browser-local presentation registry on `server-http` startup and after an interaction. That registry does not read legacy sync state, call `/api/sync`, or participate in DEVD data, archive, or backup ownership.

## Operational Boundary

DEVD in `server-http` mode resolves its formal directory from the environment,
the DEVD-owned platform configuration, or the system Documents/Tuckmark
default. `browser-static` intentionally has no compatible API implementation.

Tests use isolated temporary fixtures. Development previews reuse a valid
worktree-specific copy prepared by `bun run dev:data:prepare`, or use a newly
created empty temporary directory when no prepared copy exists. They never
default to the formal user directory.
